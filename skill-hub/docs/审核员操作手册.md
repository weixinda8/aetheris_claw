## 概述

欢迎成为 Aetheris Skill Hub 审核员！作为审核员，您在确保 Skill Hub 技能质量和安全性方面发挥着关键作用。本手册将指导您完成审核流程，提供审核标准和最佳实践。

### 审核员的重要性

审核员负责：
- ✅ 确保技能质量和安全性
- ✅ 维护社区贡献标准
- ✅ 保护用户免受恶意技能侵害
- ✅ 提供建设性反馈给开发者
- ✅ 促进技能生态健康发展

### 审核员权限

作为审核员，您可以：
- 查看审核队列中的所有技能
- 执行初级和高级审核
- 批准、拒绝或要求修改技能
- 查看技能审核历史
- 访问自动化扫描报告

## 审核流程

### 三级审核流程

Skill Hub 采用**三级审核 + 自动化扫描**的混合审核模式：

```
开发者提交
    ↓
[阶段 1] 自动化安全扫描（自动）
    ├─ 静态代码分析
    ├─ 权限检查
    ├─ 依赖漏洞扫描
    ├─ 签名验证
    └─ 结果：通过 → 阶段 2，不通过 → 反馈
    ↓
[阶段 2] 初级审核（审核员）
    ├─ 功能完整性检查
    ├─ 文档完整性检查
    ├─ 代码质量检查
    └─ 元数据准确性检查
    ↓
[阶段 3] 高级审核（资深审核员）
    ├─ 安全性深度审查
    ├─ 架构合理性评估
    ├─ 性能影响评估
    └─ 生态兼容性检查
    ↓
发布到 Skill Hub
    ↓
[阶段 4] 上线后监控（持续）
    ├─ 用户评分和评论
    ├─ 使用统计和成功率
    ├─ 安全事件监控
    └─ 定期重新审核
```

### 审核状态说明

| 状态 | 描述 | 下一步 |
|------|------|--------|
| `draft` | 草稿，仅作者可见 | 提交审核 |
| `pending` | 等待自动化扫描 | 自动进入阶段 1 |
| `automated_scan_in_progress` | 自动化扫描中 | 等待扫描完成 |
| `automated_scan_failed` | 自动化扫描失败 | 开发者修改后重新提交 |
| `junior_review_pending` | 等待初级审核 | 初级审核员审核 |
| `junior_review_in_progress` | 初级审核中 | 完成初级审核 |
| `junior_review_changes_requested` | 初级审核要求修改 | 开发者修改后重新提交 |
| `junior_review_rejected` | 初级审核拒绝 | 开发者可申诉 |
| `senior_review_pending` | 等待高级审核 | 高级审核员审核 |
| `senior_review_in_progress` | 高级审核中 | 完成高级审核 |
| `senior_review_changes_requested` | 高级审核要求修改 | 开发者修改后重新提交 |
| `senior_review_rejected` | 高级审核拒绝 | 开发者可申诉 |
| `published` | 已发布 | 上线后监控 |
| `deprecated` | 已弃用 | 仍可使用但不推荐 |
| `blocked` | 已下架 | 无法使用 |

### 审核时间 SLA

| 阶段 | 目标时间 | 最大时间 |
|------|----------|----------|
| 自动化扫描 | < 5 分钟 | 30 分钟 |
| 初级审核 | < 24 小时 | 48 小时 |
| 高级审核 | < 48 小时 | 72 小时 |
| **总时间** | **3-5 工作日** | **7 工作日** |

## 审核工具

### 访问审核仪表板

作为审核员，您可以通过审核 API 或管理界面进行审核操作。

#### 获取审核队列

```bash
curl -X GET "http://localhost:8080/api/audit/queue?stage=junior_review_pending" \
  -H "Authorization: Bearer <your-token>"
```

#### 获取审核统计

```bash
curl -X GET http://localhost:8080/api/audit/stats \
  -H "Authorization: Bearer <your-token>"
```

响应示例：
```json
{
  "pending_automated_scan": 5,
  "pending_junior_review": 12,
  "pending_senior_review": 3,
  "total_approved_this_week": 25,
  "total_rejected_this_week": 2,
  "average_review_time_hours": 4.5
}
```

审核系统集成了多种自动化扫描工具：

#### 1. 静态代码分析
- Rust Clippy 检查
- 代码风格检查
- 常见错误模式检测

#### 2. 权限检查
- 验证声明的权限
- 检测权限过度申请

#### 3. 依赖漏洞扫描

- 验证开发者 GPG 签名


## 审核标准

### 阶段 1：自动化扫描标准

技能必须通过所有自动化检查：

#### ✅ 通过标准
- 无 Clippy 错误（警告可以接受）
- 权限声明合理，无过度申请
- 无已知高危依赖漏洞
- 签名验证通过（如果已签名）
- 元数据格式正确

#### ❌ 失败标准
- 编译错误
- 高危安全漏洞
- 权限与实际使用不符
- 签名验证失败
- 元数据缺失或无效

### 阶段 2：初级审核标准

#### 功能完整性（30%）

**检查清单：**
- [ ] 技能功能与描述一致
- [ ] 输入输出符合 Schema
- [ ] 示例输入可以正常运行
- [ ] 错误处理合理
- [ ] 边界情况处理得当

**评分指南：**
- 90-100：功能完整，所有测试通过
- 70-89：功能基本完整，小问题可接受
- 50-69：功能有缺陷，需要修改
- 0-49：功能严重不完整，拒绝

#### 文档完整性（20%）

**检查清单：**
- [ ] 技能描述清晰准确
- [ ] 输入参数完整说明
- [ ] 输出格式详细说明
- [ ] 使用示例提供
- [ ] 限制和注意事项说明
- [ ] CHANGELOG 存在（如果是更新）

**评分指南：**
- 90-100：文档详尽，示例丰富
- 70-89：文档完整，基本清晰
- 50-69：文档有缺失，需要补充
- 0-49：文档严重不足，拒绝

#### 代码质量（20%）

**检查清单：**
- [ ] 代码结构清晰
- [ ] 有适当的注释
- [ ] 遵循 Rust 最佳实践
- [ ] 有单元测试
- [ ] 无明显的性能问题
- [ ] 资源使用合理

**评分指南：**
- 90-100：代码优秀，测试完整
- 70-89：代码良好，测试基本完整
- 50-69：代码一般，需要改进
- 0-49：代码质量差，拒绝

#### 元数据准确性（30%）

**检查清单：**
- [ ] 技能名称准确
- [ ] 分类选择合理
- [ ] 标签相关且有用
- [ ] 版本号符合语义化版本
- [ ] 作者信息完整
- [ ] 权限级别设置适当

### 阶段 3：高级审核标准

#### 安全性深度审查（35%）

**检查清单：**
- [ ] 无明显的安全漏洞
- [ ] 输入验证充分
- [ ] 无硬编码的密钥或凭证
- [ ] 权限使用遵循最小权限原则
- [ ] 外部调用安全
- [ ] 数据处理安全
- [ ] 有适当的错误处理（不泄露敏感信息）

**安全关注点：**
- 命令注入风险
- 路径遍历风险
- 反序列化风险
- 资源耗尽风险
- 信息泄露风险

#### 架构合理性（25%）

**检查清单：**
- [ ] 技能设计合理
- [ ] 依赖选择适当
- [ ] 性能考虑周全
- [ ] 可扩展性良好
- [ ] 与现有技能无重复
- [ ] 填补生态空白

#### 性能影响评估（20%）

**检查清单：**
- [ ] 响应时间合理
- [ ] 资源使用可控
- [ ] 有适当的超时设置
- [ ] 缓存策略合理
- [ ] 无明显的性能瓶颈

#### 生态兼容性（20%）

**检查清单：**
- [ ] 与 Aetheris 核心兼容
- [ ] 遵循技能开发规范
- [ ] 与现有技能良好协作
- [ ] 版本管理正确
- [ ] 向后兼容性考虑

### 综合审核决策

基于各维度评分，做出审核决策：

| 综合评分 | 决策 | 说明 |
|----------|------|------|
| 80-100 | ✅ 批准 | 技能优秀，可以发布 |
| 60-79 | ⚠️ 要求修改 | 技能基本合格，需要小修改 |
| 40-59 | 🔄 重新提交 | 技能需要较大修改 |
| 0-39 | ❌ 拒绝 | 技能不合格，拒绝发布 |

## 常见审核场景

### 场景 1：新技能提交

**审核要点：**
1. 检查自动化扫描报告
2. 验证功能完整性
3. 评估文档质量
4. 审查代码质量
5. 确认安全性

**操作步骤：**
```bash
# 1. 获取技能详情
curl http://localhost:8080/api/skills/<skill-id> \
  -H "Authorization: Bearer <your-token>"

# 2. 查看自动化扫描报告
curl http://localhost:8080/api/skills/<skill-id>/automated-scan-report \
  -H "Authorization: Bearer <your-token>"

# 3. 执行审核动作（批准）
curl -X POST http://localhost:8080/api/audit/skills/<skill-id>/stages/junior_review \
  -H "Authorization: Bearer <your-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "approve",
    "comment": "技能质量良好，文档完整，批准进入高级审核",
    "scores": {
      "functionality": 90,
      "documentation": 85,
      "code_quality": 88,
      "security": 92,
      "compatibility": 90
    }
  }'
```

### 场景 2：要求修改

**审核要点：**
1. 明确指出需要修改的问题
2. 提供具体的修改建议
3. 设置合理的修改期限
4. 保持建设性和鼓励性

**操作步骤：**
```bash
curl -X POST http://localhost:8080/api/audit/skills/<skill-id>/stages/junior_review \
  -H "Authorization: Bearer <your-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "request_changes",
    "comment": "技能基本良好，但需要以下修改：\n1. 补充使用示例\n2. 添加单元测试\n3. 修复 Clippy 警告\n\n请在 7 天内修改并重新提交。",
    "requested_changes": [
      "补充使用示例",
      "添加单元测试",
      "修复 Clippy 警告"
    ],
    "deadline_days": 7,
    "scores": {
      "functionality": 85,
      "documentation": 60,
      "code_quality": 75,
      "security": 80,
      "compatibility": 85
    }
  }'
```

### 场景 3：拒绝技能

**审核要点：**
1. 明确说明拒绝原因
2. 提供具体的改进建议
3. 告知申诉流程
4. 保持专业和尊重

**操作步骤：**
```bash
curl -X POST http://localhost:8080/api/audit/skills/<skill-id>/stages/junior_review \
  -H "Authorization: Bearer <your-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "reject",
    "comment": "很抱歉，此技能目前不符合发布标准。主要问题：\n1. 存在高危安全漏洞（未验证的用户输入）\n2. 功能不完整，核心功能无法正常工作\n3. 文档严重不足\n\n建议重新设计后再提交。如有疑问，可通过 GitHub Discussions 寻求帮助。",
    "rejection_reasons": [
      "存在高危安全漏洞",
      "功能不完整",
      "文档严重不足"
    ],
    "appeal_info": "如对审核结果有异议，可在 30 天内提交申诉。",
    "scores": {
      "functionality": 30,
      "documentation": 20,
      "code_quality": 40,
      "security": 10,
      "compatibility": 50
    }
  }'
```

### 场景 4：技能更新审核

**审核要点：**
1. 检查变更日志
2. 验证更新内容
3. 确保向后兼容性
4. 检查版本号是否正确
5. 评估更新的必要性

**关注点：**
- 破坏性变更是否有适当的版本号提升
- 是否有迁移指南
- 变更是否合理
- 是否影响现有用户

### 场景 5：重新审核

**审核要点：**
1. 检查修改是否完整
2. 验证问题是否解决
3. 确认没有引入新问题
4. 评估整体改进

## 审核员职责

### 日常职责

1. **处理审核队列**
   - 定期检查审核队列
   - 优先处理等待时间长的技能
   - 确保在 SLA 内完成审核

2. **提供高质量反馈**
   - 给出具体、可操作的建议
   - 保持建设性和鼓励性
   - 解释审核决策的理由

3. **维护审核标准**
   - 遵循审核标准一致
   - 记录审核决策
   - 参与审核标准讨论

4. **持续学习**
   - 了解最新的安全威胁
   - 学习新的技能开发模式
   - 参与审核员培训

### 审核行为准则

作为审核员，请遵守以下准则：

✅ **做到：**
- 公平、公正地审核所有技能
- 提供清晰、具体的反馈
- 尊重开发者的工作
- 保持专业和礼貌
- 及时完成审核任务
- 持续学习和改进

❌ **不要：**
- 基于个人偏好审核
- 给出模糊或不完整的反馈
- 贬低或嘲讽开发者
- 拖延审核任务
- 泄露未发布技能的信息
- 接受或索要好处

### 审核记录

所有审核动作都会被记录，包括：
- 审核员 ID
- 审核时间
- 审核动作（批准/拒绝/要求修改）
- 审核评论
- 各维度评分
- 请求的修改项

审核记录可通过以下方式查看：
```bash
curl -X GET http://localhost:8080/api/skills/<skill-id>/audit-history \
  -H "Authorization: Bearer <your-token>"
```

## 最佳实践

### 审核效率技巧

1. **批量处理相似技能**
   - 同类技能一起审核
   - 利用审核模板
   - 复用常见反馈

2. **使用检查清单**
   - 按照审核清单逐项检查
   - 避免遗漏重要项
   - 保持审核全面

3. **及时沟通**
   - 有疑问及时询问开发者
   - 提供进度更新
   - 澄清模糊点

### 反馈写作技巧

好的审核反馈应该：

✅ **具体**
- "第 42 行的输入没有验证"
- 而不是 "输入验证有问题"

✅ **建设性**
- "建议添加 XYZ 来改进..."
- 而不是 "这个做得不好"

✅ **可操作**
- "请补充使用示例"
- 而不是 "文档需要改进"

✅ **鼓励性**
- "整体做得很好，只需小修改"
- 而不是只指出问题

✅ **清晰**
- 使用编号列表
- 分段说明
- 突出重点

### 处理困难情况

#### 有争议的审核

1. 保持专业和冷静
2. 重申审核标准和理由
3. 提供具体的例子
4. 建议寻求资深审核员的第二意见
5. 告知申诉流程

#### 开发者不接受反馈

1. 倾听开发者的顾虑
2. 解释审核决策的依据
3. 寻找共同点
4. 必要时邀请资深审核员参与
5. 保持尊重和耐心

#### 技能质量差但开发者努力

1. 肯定开发者的努力
2. 提供详细的学习资源
3. 建议从小型技能开始
4. 提供 mentorship 机会
5. 鼓励持续学习
