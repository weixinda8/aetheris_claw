## 📊 一、Aetheris 当前定位与架构

### 1.1 Aetheris 的定位（现状）

Aetheris 目前的定位是 **企业级、生产环境优先** 的 Agent 框架，其核心特点：

| 维度 | 现状 | 说明 |
|------|------|------|
| **设计哲学** | Agent 是协调者，Skill 是能力单元 | 清晰的职责分离 |
| **配置格式** | `.skill.yaml`（纯 YAML，结构化） | 强类型、完整元数据 |
| **企业级特性** | 超时、重试、安全沙箱、强类型 | 生产环境优先 |
| **目标用户** | 企业开发者、生产环境部署 | 规范、安全、可控 |
| **架构复杂度** | 中高 | 分层架构，适合复杂业务流程 |

### 1.2 Aetheris 当前架构

```
┌─────────────────────────────────────────────────────────┐
│                     Aetheris Agent                      │
│  (协调者 - 管理流程、调用 Skill)                       │
└─────────────────┬───────────────────────────────────────┘
                  │
        ┌─────────┼─────────┐
        │         │         │
┌───────▼──┐ ┌──▼───────┐ ┌▼────────┐
│ Skill 1  │ │ Skill 2  │ │ Skill 3 │
│ (.yaml)  │ │ (.yaml)  │ │ (.yaml) │
└──────────┘ └──────────┘ └─────────┘
```

**核心设计思想：**
- Skill 只定义接口（parameters、returns）
- 流程逻辑在 Agent 配置中（system_prompt）
- 适合复杂业务流程和多 Skill 协调

## ⚔️ 二、与 agentskills.io 的根本冲突

### 2.1 定位冲突

| 维度 | Aetheris 现状 | agentskills.io 标准 | 冲突点 |
|------|--------------|-------------------|--------|
| **技能定位** | Skill = 能力单元（接口定义） | Skill = 完整智能体（指令+流程） | **核心冲突** |
| **流程位置** | 流程在 Agent 配置中 | 流程在 Skill 的 Markdown 正文中 | **职责冲突** |
| **目标场景** | 企业级、复杂业务流程 | 个人级、简单场景、快速开发 | **用户群冲突** |

### 2.2 设计哲学冲突

```
Aetheris 的设计哲学：
┌─────────────────────────────────────┐
│  Agent = 大脑（流程协调）          │
│  Skill = 手脚（能力执行）          │
│  分离关注点，适合复杂场景          │
└─────────────────────────────────────┘

agentskills.io 的设计哲学：
┌─────────────────────────────────────┐
│  Skill = 完整智能体                │
│  单个文件，简单直接                │
│  适合快速开发、简单场景            │
└─────────────────────────────────────┘
```

**这是两种完全不同的设计哲学，不是简单的格式差异！**

### 2.3 具体冲突点

#### 冲突 1：Skill 的职责边界

**agentskills.io 的 SKILL.md：**
```markdown
# Skill: PDF 处理器
## 4. 执行流程（强制）
1. 输入校验
2. 内容提取
3. 编辑处理
4. 格式转换
5. 输出打包
```
→ **流程在 Skill 内部**

**Aetheris 的 .skill.yaml：**
```yaml
parameters:
  - name: pdf_path
    type: string
returns:
  type: object
```
→ **Skill 只定义接口，流程在 Agent 中**

**冲突：** 如果 Aetheris 采用 agentskills.io，Skill 内部的执行流程如何与 Agent 的流程协调？

---

#### 冲突 2：Markdown 指令体 vs 结构化流程

**agentskills.io：** 自然语言的 Markdown 指令体，AI 理解执行
**Aetheris：** 结构化的参数和返回值定义，适合程序处理

**冲突：** Markdown 指令体的自然语言如何转换为 Aetheris 的结构化流程？

---

#### 冲突 3：allowed-tools vs Aetheris 权限模型

**agentskills.io：**
```yaml
allowed-tools: [Read, Write, Bash, CodeExecutor]
```
→ **工具白名单，简单**

**Aetheris：**
```yaml
spec:
  permissions: ["file.read", "file.write"]
  security:
    sandbox_level: "high"
```
→ **企业级安全沙箱，复杂但强大**

**冲突：** allowed-tools 如何映射到 Aetheris 的企业级权限模型？

## 🎯 五、关键洞察

### 洞察 1：这不是格式之争，是设计哲学之争

**表面上看：**
- agentskills.io：YAML Frontmatter + Markdown
- Aetheris：纯 YAML

**实际上：**
- agentskills.io：Skill = 完整智能体（个人级、快速开发）
- Aetheris：Agent 协调者 + Skill 能力单元（企业级、生产环境）

**这是两种完全不同的设计哲学，不是简单的格式转换！**

---

### 洞察 2：agentskills.io 的优势场景

| 场景 | agentskills.io | Aetheris |
|------|---------------|----------|
| **快速原型** | ✅ 优秀 | ⚠️ 复杂 |
| **个人使用** | ✅ 优秀 | ⚠️ 过重 |
| **简单技能** | ✅ 优秀 | ⚠️ 过重 |
| **跨平台共享** | ✅ 优秀 | ❌ 不兼容 |
| **企业生产** | ⚠️ 不足 | ✅ 优秀 |
| **复杂流程** | ⚠️ 不足 | ✅ 优秀 |
| **多 Skill 协调** | ❌ 不适合 | ✅ 优秀 |

---

### 洞察 3：Aetheris 的核心优势不能丢

Aetheris 的核心价值在于：
1. ✅ 清晰的分层架构（Agent 协调者 + Skill 能力单元）
2. ✅ 企业级特性（超时、重试、安全沙箱、强类型）
3. ✅ 适合复杂业务流程和多 Skill 协调
4. ✅ 生产环境优先的设计理念

**如果为了兼容 agentskills.io 而放弃这些优势，那是得不偿失的！**

## 💡 六、建议方案

### 方案 A：完全采用（不推荐）

**做法：** 废弃现有的 .skill.yaml 格式，完全转向 agentskills.io

**优点：**
- 简单、一致
- 完全符合行业标准

**缺点：**
- 放弃 Aetheris 的核心优势
- 现有用户迁移成本高
- 定位混乱

**推荐度：** ⭐（不推荐）

---

### 方案 B：完全不采用（不推荐）

**做法：** 保持现状，不支持 agentskills.io

**优点：**
- 保持 Aetheris 的核心优势
- 没有额外维护成本

**缺点：**
- 与行业标准脱节
- 无法利用生态系统
- 新用户学习曲线陡

**推荐度：** ⭐⭐（不推荐）

---

### 方案 C：可选支持 + 转换器（推荐 ⭐⭐⭐⭐⭐）

**做法：**
1. 保持现有 .skill.yaml 格式作为 **主要格式**（生产环境推荐）
2. **可选支持** agentskills.io 的 SKILL.md 格式（快速开发用）
3. 提供 **双向转换器**，但明确标注：
   - SKILL.md → .skill.yaml：适合快速原型
   - .skill.yaml → SKILL.md：适合跨平台共享
4. **文档明确说明**：
   - 生产环境：推荐 .skill.yaml
   - 快速开发/跨平台：可选 SKILL.md
5. **不尝试融合**：保持两种格式的独立性，不试图融合设计哲学

**核心思想：**
> **Aetheris 是企业级框架，.skill.yaml 是主要格式。**
> **SKILL.md 是可选的、辅助的格式，用于快速开发和跨平台共享。**
> **两种格式长期共存，但地位不同。**

**优点：**
- ✅ 保持 Aetheris 的核心优势和定位
- ✅ 可选支持行业标准，获得生态价值
- ✅ 用户可以根据场景选择合适的格式
- ✅ 风险可控，进退自如
- ✅ 定位清晰，不会混乱

**缺点：**
- ⚠️ 需要维护两套解析器（但可以接受）
- ⚠️ 用户需要理解两种格式的区别（但文档可以解决）

**推荐度：** ⭐⭐⭐⭐⭐（强烈推荐）

---

### 方案 D：核心子集支持（备选 ⭐⭐⭐⭐）

**做法：**
只支持 agentskills.io 的核心子集：
- ✅ 支持：YAML Frontmatter 字段（name、description、version 等）
- ✅ 支持：Markdown 正文（但不强制要求）
- ❌ 不支持：Markdown 强制章节结构（不适合 Aetheris 架构）
- ❌ 不支持：执行流程在 Markdown 中（保持 Aetheris 的流程在 Agent 中）

**核心思想：**
> **借用 agentskills.io 的格式和元数据，但保持 Aetheris 的架构。**

**优点：**
- ✅ 格式兼容，可以共享
- ✅ 保持 Aetheris 的核心架构
- ✅ 实现相对简单

**缺点：**
- ⚠️ 不是完整的 agentskills.io 兼容
- ⚠️ Markdown 正文可能只作为描述，不被执行

**推荐度：** ⭐⭐⭐⭐（备选方案）

## 📋 七、具体建议（方案 C 的详细）

### 7.1 定位澄清

**在文档和代码中明确声明：**

> **Aetheris 定位：** 企业级、生产环境优先的 Agent 框架  
> **主要格式：** `.skill.yaml`（推荐用于生产环境）  
> **可选格式：** `SKILL.md`（可选，用于快速开发和跨平台共享）

---

### 7.2 实现边界

| agentskills.io 特性 | Aetheris 支持方式 | 说明 |
|---------------------|------------------|------|
| SKILL.md 文件 | ✅ 可选支持 | 作为可选格式 |
| YAML Frontmatter | ✅ 完全支持 | 映射到 .skill.yaml 的 metadata |
| Markdown 正文 | ⚠️ 作为描述 | 不执行，只作为人类可读文档 |
| 强制章节结构 | ❌ 不要求 | 保持 Aetheris 架构 |
| 执行流程 | ❌ 不处理 | 流程仍在 Agent 配置中 |
| allowed-tools | ⚠️ 映射到权限 | 映射到 Aetheris 的权限模型 |
| scripts/、assets/ 等 | ✅ 可选支持 | 但不自动执行 |

**关键：Markdown 正文在 Aetheris 中只作为描述，不被执行！**

---

### 7.3 转换器设计

**SKILL.md → .skill.yaml：**
```
SKILL.md (YAML Frontmatter)
    ↓
映射到 .skill.yaml 的 metadata
    ↓
Markdown 正文作为 description 补充
    ↓
生成 .skill.yaml
```

**.skill.yaml → SKILL.md：**
```
.skill.yaml (metadata)
    ↓
映射到 SKILL.md 的 YAML Frontmatter
    ↓
生成简单的 Markdown 正文（基于现有参数）
    ↓
生成 SKILL.md
```

---

### 7.4 文档策略

**文档结构：**
1. **主要文档**：.skill.yaml 格式（详细、完整）
2. **可选文档**：SKILL.md 格式（简短、说明兼容性）
3. **转换指南**：双向转换步骤
4. **场景指南**：
   - 生产环境：使用 .skill.yaml
   - 快速原型：使用 SKILL.md
   - 跨平台共享：转换为 SKILL.md

## 🎉 八、最终结论

### 8.1 核心总结

1. **这不是格式之争，是设计哲学之争**
   - agentskills.io：Skill = 完整智能体（个人级、快速开发）
   - Aetheris：Agent 协调者 + Skill 能力单元（企业级、生产环境）
   - 两者根本不同，无法完全融合

2. **完全采用或完全不采用都有问题**
   - 完全采用：放弃 Aetheris 的核心优势
   - 完全不采用：与行业标准脱节

3. **方案 C（可选支持 + 转换器）是最优解**
   - 保持 .skill.yaml 作为主要格式
   - 可选支持 SKILL.md 作为辅助格式
   - 提供双向转换器
   - 明确文档，定位清晰

---

4. ✅ **完善文档**：明确说明两种格式的使用场景

**不推荐：**
